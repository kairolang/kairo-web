# Kairo Benchmarks: 15 Programs vs C++ and Rust

Fifteen programs written in Kairo, C++ and Rust, plus one that measures a Kairo-only feature, timed on one machine. All results are below, losses included.

One fact frames everything: Kairo compiles through Clang and LLVM. Kairo's frontend parses and type-checks the source itself, and its own Clang/LLVM 22 build is the backend. On plain arithmetic, Kairo, Clang and rustc therefore share an optimizer and a code generator, and a gap between them comes from what each frontend hands LLVM, not from the backend. Large Kairo wins come from the runtime (its mimalloc heap) or from how a language feature is lowered.

Summary: on 9 of 15 programs Kairo is within 10% of the best C++ or Rust build. It's well ahead where the heap dominates, ahead on generators, closures and the interpreter loop, and behind on nbody and, against GCC only, on virtual dispatch.

## The toolchains

- **kairo**: the Kairo compiler at `-O3`.
- **gcc** and **clang**: the C++ version built by the system GCC and Clang.
- **kcc**: the *same* C++ source built by Kairo's C++ driver. It links Kairo's runtime, including the [mimalloc](https://github.com/microsoft/mimalloc) heap that Kairo's global allocator uses. kcc is the control: when kcc closes a gap between Kairo and plain C++, the runtime caused the gap, not the language.
- **rust**: the Rust version built by `rustc`.

Kairo is red, kcc is dimmed red, the rest are gray. Every row is labeled.

## Memory

The kcc column matters most here.

<BenchChart name="btree" n="20" rows={[
  { label: 'kairo', median: 2.230, min: 2.214 },
  { label: 'kcc',   median: 3.342, min: 3.334 },
  { label: 'gcc',   median: 5.323, min: 5.286 },
  { label: 'clang', median: 5.965, min: 5.878 },
  { label: 'rust',  median: 6.200, min: 6.137 },
]} caption="kcc builds the same C++ as gcc and clang but links Kairo's runtime heap. That alone takes it from 5.3 s to 3.3 s." />

btree builds and frees millions of small binary trees, one heap allocation per node. Kairo is 2.7× faster than Clang, and most of that is the allocator. `@create` goes to the [global allocator](/docs/language/allocators/#global-allocator), which is mimalloc's small-object path; the GCC, Clang and Rust builds use glibc `malloc`.

kcc separates the two effects. The same C++ linked against Kairo's runtime drops from 5.3 s to 3.3 s, so most of the gap is the heap. Kairo is still 1.5× faster than kcc. Part of that is the free path: Kairo frees with the size and alignment it already knows (`destroy` calls mimalloc's sized small-object free directly, 3 instructions on the hot path), while C++ `delete` goes through `operator delete` to an unsized `free`, which has to look up the block's page first.

<BenchChart name="alloc" n="50000000" baseline="clang-malloc" rows={[
  { label: 'kairo',        median: 0.121, min: 0.119 },
  { label: 'kcc-malloc',   median: 0.126, min: 0.125 },
  { label: 'kcc-new',      median: 0.135, min: 0.130 },
  { label: 'clang-malloc', median: 0.201, min: 0.200 },
  { label: 'gcc-malloc',   median: 0.202, min: 0.200 },

  { label: 'gcc-new',      median: 0.269, min: 0.265 },
  { label: 'clang-new',    median: 0.272, min: 0.266 },
]} />

alloc creates and destroys one 16-byte object 50 million times; the C++ is built once with `new`/`delete` and once with `malloc`/`free`. It's the cleanest allocator comparison in the set. Kairo and kcc-malloc are within 4% of each other and 1.6× faster than glibc `malloc`. A Kairo `create`/`destroy` pair is 49 instructions, against 146 for glibc `malloc`/`free` and 157 for `new`/`delete`. Through glibc, `new`/`delete` costs a third more than `malloc`/`free`; through Kairo's runtime, 7% more.

<BenchChart name="nullable" n="10000000" rows={[

nullable builds a 10-million-node linked list with nullable `next` links, walks and searches it 50 times, then frees it. kcc is within 4% of Kairo, and both are 1.5× ahead of the rest, so most of this one is the heap.

The remaining few percent is the free path, as in btree. Kairo's `@destroy` frees each node with the size and alignment it already knows, through the runtime's sized free. The C++ list is a chain of `std::unique_ptr`: in kcc's build, `unique_ptr::reset` stays an out-of-line call (seven call sites in `main`), and each node goes through `operator delete` to an unsized `free`.

## Abstractions

Stored closures, virtual calls, generators, generic code, and an interpreter loop over `match`.

<BenchChart name="closures" n="1000000000" rows={[

  { label: 'gcc',   median: 5.370, min: 5.355 },

closures calls three capturing callbacks stored in an array, a billion times. All three languages use a type-erased callable: Kairo's `fn` values, Rust's `Box<dyn Fn>`, and `std::function` in C++, which is what C++ uses when a callback has to be stored. Kairo is 6% faster than Rust; `std::function` is 3.4× slower with Clang and 7.3× slower with GCC. A C++ template that takes the lambda directly would inline, but then the callback isn't stored.

<BenchChart name="dispatch" n="1500000" rows={[

  { label: 'kcc',   median: 2.316, min: 2.309 },

dispatch makes virtual calls over a mixed array of 1,024 shapes. GCC is 2.5× faster than Kairo, Clang and Rust, which all finish in 2.03 s. Kairo matching Clang here is expected, since Kairo classes share the C++ vtable ABI and their virtual calls go through the same backend as Clang's. GCC is the outlier because of speculative devirtualization: the derived classes are `final`, so GCC knows the complete set of three overriders and can replace the indirect call with type checks and inlined bodies.

<BenchChart name="gen" n="1000000000" rows={[

gen is a three-stage pipeline of nested generators summing a billion values: `-> yield T` in Kairo, C++20 coroutines in C++, iterator adapters in Rust. Kairo generators are built on the same coroutine machinery as C++20 coroutines, so Kairo and the Clang row share it. In both, Clang elides the coroutine frames' heap allocations and inlines the whole pipeline into the caller's loop. GCC doesn't perform that elision, which is why its row is 6.6× slower. Kairo is 1.2× ahead of Clang and 1.7× ahead of Rust. The difference between Kairo and Clang is Kairo's promise type and how `yield` is lowered. Like fannkuch, gen has one outlier run (0.451 s, 20% under the median).

Rust's `sort_unstable` (pattern-defeating quicksort) is 2.9× faster than libstdc++'s `std::sort` (introsort), and that's the target for Kairo's.

## Errors and formatting

Kairo's two largest wins.

<BenchChart name="errpath" n="500000000" rows={[
  { label: 'kairo', median: 0.222, min: 0.220 },
  { label: 'rust',  median: 0.564, min: 0.562 },
  { label: 'clang', median: 2.262, min: 2.237 },
  { label: 'gcc',   median: 2.341, min: 2.317 },
  { label: 'kcc',   median: 8.209, min: 8.140 },
]} />

errpath makes 500 million calls, 1% of which fail: `panic`/`try`/`catch` in Kairo, exceptions in C++, `Result` in Rust. Kairo is 10× faster than C++ exceptions and 2.5× faster than Rust's `Result`.

A Kairo `panic` is a returned value, not an unwind, so LLVM treats the failure path like any other branch. In the Kairo build `parse` and `fail` are inlined into the loop, `x % 100 == 0` becomes a multiply-and-rotate test, `x * 3` becomes a running `+= 3`, and no error value is ever built. Rust's `Result` gets the same treatment, so the gap to Rust is loop shape, not error handling. Rust's `1..=n` adds an exhaustion check to every iteration, and LLVM computes both outcomes and picks one with `cmov` instead of branching: 18 instructions per iteration against Kairo's 13 on the success path, and Kairo's branch is predicted right 99% of the time. The C++ builds pay for 5 million `throw`s, each one allocating the exception (`__cxa_allocate_exception`) and unwinding to the `catch`.

The kcc row is a bug in kcc's link, not a cost of exceptions: the same code is 3.5× slower than GCC's build.

<BenchChart name="fmt" n="10000000" rows={[
  { label: 'kairo', median: 0.110, min: 0.107 },
  { label: 'kcc',   median: 0.247, min: 0.246 },

fmt converts 10 million `f64`s and 10 million `i64`s to text: f-strings in Kairo, `std::to_chars` in C++, `write!` in Rust. Kairo is 2.2× faster than kcc and 3.0× faster than Clang. Kairo's f-strings format into a buffer with 128 bytes of inline storage, so short results never touch the heap, and floats with no format spec are written directly into that buffer.

## Scoped allocators (Kairo only)

scopes has no C++ or Rust version; it measures Kairo's [scoped allocator](/docs/language/allocators/#scoped-allocator) stack. It opens `DEPTH` nested allocator scopes, then runs 50 million operations at the innermost level. Times per operation:

| Operation | depth 1 | depth 16 | depth 64 |
|---|---:|---:|---:|
| allocate + free in the innermost scope | 2.5 ns | 2.5 ns | 2.7 ns |
| free a global block inside the scopes | 3.1 ns | 3.1 ns | 3.1 ns |
| free a block from the outermost scope | 1.4 ns | 7.2 ns | 21.6 ns |
| open and close one more scope | 6.2 ns | 6.6 ns | 6.6 ns |

`free` has to find which open scope, if any, owns an address. The scope stack keeps a bounding box over every open scope's memory, so an address outside it (a global block) is rejected with one range check, at any depth. An address inside the box is found by scanning the open scopes from innermost outward, so freeing a block that belongs to the outermost scope costs 0.3 to 0.4 ns for every scope above it: a few nanoseconds at realistic depths, 22 ns at 64.

## Method

The code is in [`Tests/bench`](https://github.com/kairolang/kairo/tree/main/Tests/bench). Each program is written the way that language's code is normally written; the README lists what each version uses (`std::function` vs `Box<dyn Fn>`, exceptions vs `Result`, and so on). None is tuned for a particular compiler.

- **Builds:** `-O3` for Kairo, GCC, Clang and kcc (`-std=c++20` for C++); `-C opt-level=3 -C codegen-units=1` for Rust. No `-march=native`, LTO or PGO.
- **Timing:** `bench-seq.fish 8` builds and times one benchmark at a time. Toolchains are interleaved within a benchmark (each binary once, then each again) for eight rounds, so a background-load swing hits all of them.
- **Measured:** wall-clock time of the whole process, startup and output included.
- **Correctness:** each benchmark prints a checksum; the harness checks every toolchain prints the same one. All sixteen agreed.
- **Machine:** AMD Ryzen 9 7900X (12 cores / 24 threads), Linux 7.2.11-zen1, GCC 16.2.1, Clang 23.1.3, rustc 1.98.1, Kairo at commit `f66b5057` (Clang/LLVM 22 backend).

## Limits

- Eight runs. Most medians are within 1 to 2% of the fastest run (Kairo's fannkuch and gen are the exceptions). Don't rank differences under 5%.
- Each language uses its default allocator and standard library. That's why btree, alloc and nullable look the way they do, and why kcc is in the table.
- Some Kairo sources work around open compiler bugs: `gsort.k` wraps `i64` in a `Key` struct, `gen.k` yields only named variables, and `spectral.k` avoids one parameter name. The README lists them.
- Single-threaded micro-benchmarks. No threads, I/O, or large programs.

If you run the suite on other hardware, especially ARM, send me the results.
