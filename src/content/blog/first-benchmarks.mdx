# Kairo Benchmarks: 16 Programs vs C++ and Rust

I wrote the same sixteen small programs in Kairo, C++ and Rust and timed them on my machine. This post shows every result, including the ones where Kairo loses badly, and explains which wins come from the language and which come from something else.

Short version: on most compute-bound programs Kairo is within 10% of the best C++ or Rust build. It's well ahead wherever the heap or error handling dominates. It's clearly behind on three: virtual dispatch, generators, and nbody.

## The toolchains

- **kairo**: the Kairo compiler at `-O3`.
- **gcc** and **clang**: the C++ version built by the system's GCC and Clang.
- **kcc**: the *same* C++ source built by Kairo's C++ driver, which links Kairo's runtime, including its [mimalloc](https://github.com/microsoft/mimalloc) heap. kcc is the control: when kcc closes the gap between Kairo and plain C++, the gap came from the runtime, not from Kairo's code generation.
- **rust**: the Rust version built by `rustc`.

In the charts, Kairo is red, kcc is dimmed red, and everything else is gray. Every row is labelled, so you don't need the colours to read them.

## Memory

This is where Kairo's numbers look best. It's also where the kcc column matters most.

<BenchChart name="btree" n="20" rows={[
  { label: 'kairo', median: 1.598, min: 1.588 },
  { label: 'kcc',   median: 2.275, min: 2.261 },
  { label: 'gcc',   median: 5.587, min: 5.439 },
  { label: 'clang', median: 6.095, min: 5.988 },
  { label: 'rust',  median: 6.382, min: 6.186 },
]} caption="kcc builds the same C++ as gcc and clang but links Kairo's runtime heap. That alone takes it from 5.6 s to 2.3 s." />

**btree** builds and frees millions of small binary trees, one heap allocation per node. Kairo is 3.5× faster than GCC, but most of that is the allocator. `@create` goes to the [global allocator](/docs/language/allocators/#global-allocator), which is the runtime's bundled mimalloc, while the GCC, Clang and Rust builds use glibc's `malloc`.

kcc separates the two effects. The identical C++ program, linked against Kairo's runtime, drops from 5.6 s to 2.3 s. Most of the gap is the heap. Kairo is still 1.4× faster than kcc, though. In a first draft of this post I guessed that with mimalloc on both sides the gap would mostly disappear. It didn't, and I don't yet know where the remaining 1.4× comes from.

**alloc** creates and destroys one 16-byte object, 50 million times. The C++ is built twice, once with `new`/`delete` and once with `malloc`/`free`. This is the cleanest allocator comparison in the set, and it agrees with btree: Kairo and kcc with `malloc` are within 4% of each other, about 1.6× faster than glibc's `malloc`. Through glibc, `new`/`delete` costs another 35% on top of `malloc`. Through Kairo's runtime it costs about 9%.

**nullable** builds a 10-million-node linked list with nullable `next` links, walks and searches it 50 times, then frees it. It looks like btree: kcc gets most of the way there, and Kairo is 12% ahead of kcc and 1.7× ahead of the rest.

## Abstractions

These measure what common abstractions cost: stored closures, virtual calls, generators, generic code, and an interpreter loop built on `match`.

<BenchChart name="closures" n="1000000000" rows={[

  { label: 'kcc',   median: 2.675, min: 2.671 },
  { label: 'gcc',   median: 5.437, min: 5.386 },

**closures** applies three capturing callbacks stored in an array, a billion times. Kairo's `fn` values and Rust's `Box<dyn Fn>` are close: Kairo is 5% faster. The C++ version uses `std::function`, which is what C++ code reaches for when a callback has to be stored, and it's 3.4× slower with Clang and 7.3× slower with GCC. A C++ template taking the lambda directly would inline and be much faster, but that isn't a stored callback any more.

**dispatch** makes virtual calls over a mixed array of 1,024 shapes. This is Kairo's worst result: GCC is 2.6× faster than Kairo. But GCC is also 2.5× faster than Clang and Rust, so this is GCC doing something nobody else does, not Kairo doing something wrong. The C++ classes are marked `final`, and the likely explanation is GCC's speculative devirtualization: with only three possible targets, it can turn the virtual call into a type check and an inlined body. Against Clang and Rust, Kairo is 7–8% behind.

## Errors and text

The two biggest wins, and the two I trust least until I've looked closer.

<BenchChart name="errpath" n="500000000" rows={[
  { label: 'kairo', median: 0.226, min: 0.221 },
  { label: 'rust',  median: 0.568, min: 0.563 },
  { label: 'clang', median: 2.255, min: 2.221 },
  { label: 'gcc',   median: 2.347, min: 2.318 },
  { label: 'kcc',   median: 8.080, min: 7.992 },
]} />

**errpath** makes 500 million calls, 1% of which fail: `panic`/`try`/`catch` in Kairo, exceptions in C++, `Result` in Rust. Kairo is 10× faster than C++ exceptions, so whatever `panic` does, it isn't C++ unwinding. More surprising, it's also 2.5× faster than Rust's `Result`, which is about the cheapest error path there is. All five agree on the output, so the work is being done. But I want to see the generated code before claiming a 2.5× advantage over Rust. The kcc row needs a look too: the same exceptions code is 3.4× slower with Kairo's runtime than with GCC's.

<BenchChart name="fmt" n="10000000" rows={[
  { label: 'kairo', median: 0.129, min: 0.102 },
  { label: 'kcc',   median: 0.248, min: 0.245 },
  { label: 'clang', median: 0.327, min: 0.324 },
  { label: 'gcc',   median: 0.334, min: 0.332 },
  { label: 'rust',  median: 0.587, min: 0.586 },

**fmt** turns 10 million `f64`s and 10 million `i64`s into text: f-strings in Kairo, `std::to_chars` in C++, `write!` in Rust. Kairo's median is 1.9× faster than kcc and 2.6× faster than GCC. It's also the noisiest result in the set, with the best run 21% under the median. Kairo builds a new string for every number, while `to_chars` writes into a stack buffer, so a 2× lead is not what I'd have predicted. As with errpath, I'll check what the compiler made of the loop before leaning on it.

## Scoped allocators (Kairo only)

**scopes** has no C++ or Rust version, because it measures a Kairo feature: the [scoped allocator](/docs/language/allocators/#scoped-allocator) stack. It opens `DEPTH` nested allocator scopes, then runs 50 million operations at the innermost level. Times are per operation:

| Operation | depth 1 | depth 16 | depth 64 |
|---|---:|---:|---:|
| allocate + free in the innermost scope | 2.4 ns | 2.4 ns | 2.4 ns |
| free a global block inside the scopes | 3.0 ns | 2.9 ns | 2.9 ns |
| free a block from the outermost scope | 1.2 ns | 8.2 ns | 28.1 ns |
| open and close one more scope | 5.3 ns | 5.9 ns | 6.1 ns |

Three of the four operations cost the same at any depth, including freeing a global block while scopes are open. Freeing a block that belongs to the *outermost* scope doesn't: `free` has to find the scope that owns the address, and that costs roughly 0.45 ns for every scope opened above it. At realistic depths that's a few nanoseconds. At 64 scopes deep it's 28. Now that cost has a number.

## How the numbers were made

The code is in [`Tests/bench`](https://github.com/kairolang/kairo/tree/main/Tests/bench) in the Kairo repository. Each program is written idiomatically in each language, with the README listing what each version uses (`std::function` vs `Box<dyn Fn>`, exceptions vs `Result`, and so on), and none is tuned for one compiler.

- **Builds:** `-O3` for Kairo, GCC, Clang and kcc (`-std=c++20` for C++), and `-C opt-level=3 -C codegen-units=1` for Rust. No `-march=native`, LTO or PGO for anyone.
- **Timing:** `bench-seq.fish 4` builds and times one benchmark at a time. Within a benchmark, the toolchains are interleaved (each binary once, then each again) for four rounds, so a background-load swing hits all of them equally.
- **What's measured:** wall-clock time for the whole process, startup and output included.
- **Correctness:** each benchmark prints a checksum, and the harness checks that every toolchain prints the same one. All sixteen agreed.
- **Machine:** AMD Ryzen 9 7900X (12 cores / 24 threads), Linux 7.2.11-zen1, GCC 16.2.1, Clang 23.1.3, rustc 1.98.1, and a local build of the Kairo compiler and kcc.

## What this doesn't tell you

- **Four runs is a small sample.** Most medians sit within 1–2% of the best run, but anything under about 5% shouldn't be read as a ranking.
- **Defaults, not best effort.** Each language uses its default allocator and standard library, because that's what you get when you write the obvious code. That's exactly why btree, alloc and nullable look the way they do. kcc is there to show how much of that is the heap.
- **Some Kairo sources carry workarounds** for compiler bugs still open: `gsort.k` wraps `i64` in a `Key` struct, `gen.k` yields only named variables, and `spectral.k` avoids one parameter name. None should change the timing much, but they're listed in the README.
- **Single-threaded micro-benchmarks only.** None of this covers threads, I/O, or large programs.

If you run the suite on your own hardware and get different results, I'd like to see them, especially on ARM.
