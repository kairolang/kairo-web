# Kairo Benchmarks: 16 Programs vs C++ and Rust

I wrote the same sixteen small programs in Kairo, C++ and Rust and timed them on my machine. Every result is here, including the ones where Kairo loses badly, along with my best read of which wins come from the language and which come from something else, like the allocator.

On most compute-bound programs Kairo is within 10% of the best C++ or Rust build. It's well ahead wherever the heap or error handling dominates, and clearly behind on nbody and, against GCC only, on virtual dispatch.

## The toolchains

- **kairo**: the Kairo compiler at `-O3`.
- **gcc** and **clang**: the C++ version built by the system's GCC and Clang.
- **kcc**: the *same* C++ source built by Kairo's C++ driver, which links Kairo's runtime, including its [mimalloc](https://github.com/microsoft/mimalloc) heap. That makes it a control: when kcc closes the gap between Kairo and plain C++, the runtime was responsible for it.
- **rust**: the Rust version built by `rustc`.

In the charts, Kairo is red, kcc is dimmed red, and everything else is gray. Every row is labelled as well.

## Numeric loops

These benchmarks don't allocate. They measure how well each compiler turns plain arithmetic and array loops into machine code, and this is where Kairo has the least to show yet.

## Memory

This is where Kairo's numbers look best, and where the kcc column matters most.

<BenchChart name="btree" n="20" rows={[
  { label: 'kairo', median: 2.230, min: 2.214 },
  { label: 'kcc',   median: 3.342, min: 3.334 },
  { label: 'gcc',   median: 5.323, min: 5.286 },
  { label: 'clang', median: 5.965, min: 5.878 },
  { label: 'rust',  median: 6.200, min: 6.137 },
]} caption="kcc builds the same C++ as gcc and clang but links Kairo's runtime heap. That alone takes it from 5.3 s to 3.3 s." />

btree builds and frees millions of small binary trees, one heap allocation per node. Kairo is 2.7× faster than Clang, but most of that is the allocator. `@create` goes to the [global allocator](/docs/language/allocators/#global-allocator), which is the runtime's bundled mimalloc, while the GCC, Clang and Rust builds use glibc's `malloc`.

kcc separates the two effects. The identical C++ program, linked against Kairo's runtime, drops from 5.3 s to 3.3 s, so most of the gap is the heap. Kairo is still 1.5× faster than kcc, though. In a first draft of this post I guessed that with mimalloc on both sides the gap would mostly disappear. It didn't, and I don't yet know where the remaining 1.5× comes from.

<BenchChart name="alloc" n="50000000" baseline="clang-malloc" rows={[

alloc creates and destroys one 16-byte object, 50 million times. The C++ is built twice, once with `new`/`delete` and once with `malloc`/`free`. This is the cleanest allocator comparison in the set, and it agrees with btree: Kairo and kcc with `malloc` are within 4% of each other, about 1.6× faster than glibc's `malloc`. Through glibc, `new`/`delete` costs about a third more than `malloc`. Through Kairo's runtime it costs about 7% more.

nullable builds a 10-million-node linked list with nullable `next` links, walks and searches it 50 times, then frees it. Here kcc gets almost all the way there: Kairo is 4% ahead of kcc and 1.5× ahead of the rest.

## Abstractions

These measure what common abstractions cost: stored closures, virtual calls, generators, generic code, and an interpreter loop built on `match`.

<BenchChart name="closures" n="1000000000" rows={[

  { label: 'kcc',   median: 2.656, min: 2.646 },
  { label: 'gcc',   median: 5.370, min: 5.355 },

closures applies three capturing callbacks stored in an array, a billion times. Kairo's `fn` values and Rust's `Box<dyn Fn>` are close: Kairo is 6% faster. The C++ version uses `std::function`, which is what C++ code reaches for when a callback has to be stored, and it's 3.4× slower with Clang and 7.3× slower with GCC. A C++ template taking the lambda directly would inline and be much faster, but that isn't a stored callback any more.

dispatch makes virtual calls over a mixed array of 1,024 shapes. This is Kairo's worst result: GCC is 2.5× faster than Kairo. But GCC is also 2.5× faster than Clang and Rust, so GCC is the outlier here. The C++ classes are marked `final`, and the likely explanation is GCC's speculative devirtualization: with only three possible targets, it can turn the virtual call into a type check and an inlined body. ## Errors and text

These are Kairo's two biggest wins, and also the two I trust least.

<BenchChart name="errpath" n="500000000" rows={[
  { label: 'kairo', median: 0.222, min: 0.220 },
  { label: 'rust',  median: 0.564, min: 0.562 },
  { label: 'clang', median: 2.262, min: 2.237 },
  { label: 'gcc',   median: 2.341, min: 2.317 },
  { label: 'kcc',   median: 8.209, min: 8.140 },
]} />

errpath makes 500 million calls, 1% of which fail: `panic`/`try`/`catch` in Kairo, exceptions in C++, `Result` in Rust. Kairo is 10× faster than C++ exceptions, so whatever `panic` does, it isn't C++ unwinding. More surprising, it's also 2.5× faster than Rust's `Result`, which is about the cheapest error path there is. All five agree on the output, so the work is being done. But I want to see the generated code before claiming a 2.5× advantage over Rust. The kcc row needs a look too: the same exceptions code is 3.5× slower with Kairo's runtime than with GCC's.

<BenchChart name="fmt" n="10000000" rows={[
  { label: 'kairo', median: 0.110, min: 0.107 },
  { label: 'kcc',   median: 0.247, min: 0.246 },

  { label: 'gcc',   median: 0.336, min: 0.331 },
  { label: 'rust',  median: 0.589, min: 0.580 },

fmt turns 10 million `f64`s and 10 million `i64`s into text: f-strings in Kairo, `std::to_chars` in C++, `write!` in Rust. Kairo is 2.2× faster than kcc and 3.0× faster than Clang. Kairo builds a new string for every number, while `to_chars` writes into a stack buffer, so a lead this size is not what I'd have predicted. As with errpath, I'll check what the compiler made of the loop before leaning on it.

## Scoped allocators (Kairo only)

scopes has no C++ or Rust version, because it measures a Kairo feature: the [scoped allocator](/docs/language/allocators/#scoped-allocator) stack. It opens `DEPTH` nested allocator scopes, then runs 50 million operations at the innermost level. Times are per operation:

| Operation | depth 1 | depth 16 | depth 64 |
|---|---:|---:|---:|
| allocate + free in the innermost scope | 2.5 ns | 2.5 ns | 2.7 ns |
| free a global block inside the scopes | 3.1 ns | 3.1 ns | 3.1 ns |
| free a block from the outermost scope | 1.4 ns | 7.2 ns | 21.6 ns |
| open and close one more scope | 6.2 ns | 6.6 ns | 6.6 ns |

Three of the four operations cost nearly the same at any depth, including freeing a global block while scopes are open. Freeing a block that belongs to the *outermost* scope doesn't: `free` has to find the scope that owns the address, and that costs roughly 0.3 to 0.4 ns for every scope opened above it. At realistic depths that's a few nanoseconds. At 64 scopes deep it's 22.

## How the numbers were made

The code is in [`Tests/bench`](https://github.com/kairolang/kairo/tree/main/Tests/bench) in the Kairo repository. Each program is written idiomatically in each language, with the README listing what each version uses (`std::function` vs `Box<dyn Fn>`, exceptions vs `Result`, and so on), and none is tuned for one compiler.

- **Builds:** `-O3` for Kairo, GCC, Clang and kcc (`-std=c++20` for C++), and `-C opt-level=3 -C codegen-units=1` for Rust. No `-march=native`, LTO or PGO for anyone.
- **Timing:** `bench-seq.fish 8` builds and times one benchmark at a time. Within a benchmark, the toolchains are interleaved (each binary once, then each again) for eight rounds, so a background-load swing hits all of them equally.
- **What's measured:** wall-clock time for the whole process, startup and output included.
- **Correctness:** each benchmark prints a checksum, and the harness checks that every toolchain prints the same one. All sixteen agreed.
- **Machine:** AMD Ryzen 9 7900X (12 cores / 24 threads), Linux 7.2.11-zen1, GCC 16.2.1, Clang 23.1.3, rustc 1.98.1, and a local build of the Kairo compiler and kcc.

## What this doesn't tell you

- Eight runs is a small sample. Most medians sit within 1 to 2% of the best run (Kairo's fannkuch and gen are the exceptions), but don't read a difference under about 5% as a ranking.
- Each language uses its default allocator and standard library, because that's what you get when you write the obvious code. That's why btree, alloc and nullable look the way they do, and kcc is there to show how much of it is the heap.
- Some Kairo sources carry workarounds for compiler bugs that are still open: `gsort.k` wraps `i64` in a `Key` struct, `gen.k` yields only named variables, and `spectral.k` avoids one parameter name. None should change the timing much, but they're listed in the README.
- These are single-threaded micro-benchmarks. None of them covers threads, I/O, or large programs.

If you run the suite on your own hardware and get different results, I'd like to see them, especially on ARM.
